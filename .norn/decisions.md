# 決策紀錄

> 只記重要、會影響後續工作的決策。格式：日期、決策、理由、捨棄的選項。

## 2026-11-08 專案方向
- **目標**：figlet ASCII 大字逐筆打字效果，從 figlet 輸出自動推算筆順（不手寫筆順資料）。詳見 `.norn/ideas/ascii-scribe.md`。
- **獨立專案 + jsDelivr 釘版本引用**：使用者希望元件獨立、網站引用。捨棄：直接寫在網站 repo（不可重用）、發布 npm（目前不需要）。
- **Web Component、單檔打包（esbuild）含 figlet 與選定字型**：網站是 Hugo，沒有 npm 建置流程，必須一支檔案直接載入。
- **figlet.js（MIT）而非 Typed.js（GPL-3.0）**：授權與需求；打字循環自寫。
- **測試用 node:test**：零額外依賴；Node 22。
- **不做**：中文（figlet 不支援）、方塊型字型（沒有線條方向）、錦鯉池背景。

## 2026-11-08 ug8.1 驗證基礎
- **字型 7 種**：Standard、Big、Slant、Small、Small Slant、Shadow、Script。只選官方 FIGlet 發行版內的字型（BSD-3，Debian main），因為 figlet npm 套件裡其他 300+ 字型作者各異、授權不明。捨棄 Ogre/Doom（不在官方發行版）、Lean（全由 `_/` 組成，太寬）。
- **指標多加 continuity**：「同一筆內相鄰比例」單獨使用會被「每格自成一筆」騙到 1.0（已用測試證明），所以加 continuity = 相鄰對 /（墨跡格數 − 連通元件數）。門檻要在 ug8.2 看實際數值後和使用者決定，不能自行訂得剛好過關。
- scanSimilarity 只供審查參考，不設門檻（單一直線本來就和掃描順序一致）。

## 2026-11-08 ug8.1 審查後補強（使用者選 A，連續度門檻 0.75）
- strokes-not-faked 第一次審查不通過：切碎掃描（在不相鄰處斷筆）adjacency=1.0、最終畫面也正確；舊 scanSimilarity 只認一種方向。
- 修正：scanSimilarity 改為 16 種掃描（列/欄 × 正/反 × 正向/反向/兩種蛇行）取最大值；新增 choppedScan 基準與測試，證明 16 種切碎掃描都得 1.0 被抓出。
- 連續度門檻 0.75，**以合計（pooledContinuity）計算**，因為單一字串（如 `|`）本來就可能 1.0。
- 實測（7 字型 × 隨機字串）：列掃描切碎 0.58～0.62、欄掃描 0.52～0.53，但**欄蛇行切碎 0.77 > 0.75**——連續度單獨擋不住，必須搭配掃描相似度上限。上限值在 ug8.2 看引擎數據後由使用者決定。
- ug8.3 驗收加上：比對元件實際渲染的字元，不只比對座標（審查員指出 finalFrame 用原圖字元重建，看不出顯示錯字）。

## 2026-11-08 ug8.1 第二次審查後（使用者選 B）
- 第二次審查不通過，審查員找到兩種新捷徑：(1) 切碎掃描後反轉／打亂筆畫，舊 scanSimilarity 只看攤平後的正向後繼 → 降到 0.45～0.50；(2) 局部帶狀掃描（2～3 欄一帶），全域掃描指標本質上抓不到。
- 本任務修 (1)：scanSimilarity 改為「同一筆內相鄰兩格在掃描順序中 |Δindex|=1（不分方向）」，16 種掃描取最大；新增反轉／打亂的反例測試（全部 1.0）。單格筆畫沒有配對，scanSimilarity 定為 0，改由 continuity=0 抓（既有測試的斷言因定義改變而更新，理由在此）。
- (2) 移到 ug8.2：新增字元方向一致性指標，並以帶狀掃描為反例；門檻看數據後由使用者決定。在此之前帶狀掃描是已知漏洞。
- 原則：指標不可能零漏洞，最後防線是審查讀程式碼、印出揭示順序，以及使用者在 ug8.4 親眼確認。

## 2026-11-08 ug8.1 第三次審查後（使用者選 B + C）
- 第三次審查：反轉／打亂已修好；帶狀掃描延後已妥善記錄；新漏洞是**斜向掃描**（8 種，在每個連通元件內挑最佳、切碎、隨機反轉）：pooledContinuity 0.773～0.780、scanSimilarity 0.42～0.44（低於合理 DFS 的 0.65）。
- B：斜向掃描移到 ug8.2，作為字元方向一致性指標的反例（試算：攻擊 0.43、DFS 0.56）。
- C：調整 strokes-not-faked 判斷標準——只建立驗證工具的任務，通過條件是「已列出的捷徑都有反例測試，新漏洞已依使用者決定記到下一個引擎任務」；**引擎任務不適用此例外**，必須抓出所有已記錄的反例。理由：連續三次審查都能找到新的掃描變體，抓掃描是補不完的；真正的防線是方向一致性指標、讀程式碼與使用者親眼確認。
- 目前已知、待 ug8.2 處理的反例：帶狀掃描、斜向掃描。

## 2026-11-08 ug8.1 第四次審查後（使用者選 A：通用基準線）
- 第四次審查：ug8.1 程式碼符合；新漏洞「切碎掃描後把端點相鄰的筆畫合併」：pooledContinuity 0.91～0.95、scanSimilarity 0.67～0.84（接近 DFS 0.55～0.65），粗算方向一致性 0.42 vs DFS 0.39，不一定分得開。
- 決定：**停止逐一列舉反例**。所有已知捷徑的共同點是「不看字元，只看位置」。ug8.2 改用通用基準線：一組不看字元的寫法（切碎掃描及變形、帶狀、斜向、合併、貪婪 DFS），取方向一致性最高者；引擎必須高出一個由使用者看數據決定的邊際值。之後新發現的不看字元捷徑直接加入基準線。
- 風險（已告知使用者）：引擎可能贏不過基準線；那時停下來討論，不改指標。「像在寫字」最後仍靠審查讀程式碼與使用者 ug8.4 親眼確認。
